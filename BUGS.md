### BUG-224 — every agent played one hand and came home with a YOU LOST screen — FIXED on fix/agent-5
From Jens's prod session, after the household drained to empty overnight. **Nothing was broken. Three deliberate, correct numbers were meeting**, which is why AGENT-4 fixing the two things that WERE broken (BUG-220's rest, BUG-221's food) did not stop it happening:

* `stamina.js` `staminaStage` has HYSTERESIS: once `'worn'` he stays worn until the reserve is back to `SETTLED_AT` (67), **not** until it clears `WORN_AT` (34). That is deliberate and load-bearing — without it a sleeping agent flickers in and out of the kitchen game for ever.
* `table.js` ~3183, the SERVER-3 session stop rule, marks a CASINO seat `leaving` with `seatEndReason = 'worn'` the moment the combined stage reads worn after any hand.
* so a man deployed at any reserve under 67 whose record last said worn is worn on hand ONE and stood straight back up — with his buy-in already spent. Log line: `seat N is worn after 1 hand(s) — ending his session`.

`SNACK_STAMINA` is 25, so from empty it takes THREE snacks to clear the floor and nothing in the product said so. Two snacks put him at 50: past `WORN_AT`, short of `SETTLED_AT`, still asleep, still refused — and an owner who had just paid twice had no way to know.

**Fix, four parts.** (1) `src/server/restFloor.js` and a gate inside `seatAI`, beside AGENT-4's one-table check and for the same reason — it is the only function in the codebase that seats an agent, so the invariant is stated once and every door inherits it, including the next one somebody adds. The floor is `SETTLED_AT`, because `reserve >= 67` is precisely `stage === 'fresh'` for a worn record and a rested one alike: he sits down when he is rested, against the same threshold the hysteresis uses to let him get up. CASINO ONLY — the stop rule is a casino rule and a floor at home would empty the flat of everyone merely 'settled'. (2) `deployAgent` asks the same question above the pocket gate, so a refusal costs nothing and arrives with a body rather than a thrown string. (3) The refusal NAMES THE REMEDY and the number, in his own voice via `NATURE_WANT_LINES`, and carries LIFE-2's `.action` / `.actionLabel` so one tap feeds him or puts him to bed; an empty or half-stocked shelf sets `needs: 'stock'` and says how many to buy. (4) The ceremony reads `seatEndReason`: a session that ended worn says WORN OUT and repeats the same sentence, with the chip result demoted rather than removed.

**Self-recovery, answered:** an agent already at zero comes back on his own in `67 / 22 = 3.05` hours out of a seat. Recovery is credited ON READ rather than by a scheduler (`stamina.js` rule 2), so nothing has to be running and nobody has to press anything.

Two further faults were found BY the end-to-end walk rather than by reading, and both are fixed in the product: the gate read the reserve as `resting: true` unconditionally, so three hours at the KITCHEN TABLE were credited as three hours of sleep (the kitchen table is the one seat that does not set `activeTableId` — `presentAgent`'s own trap); and the remedy preferred the clock over the shelf, so after two of three snacks he was told to go and have a lie down with the third one sitting in the fridge he had just been sold. Regression: `scripts/verify-rest-floor.js` (fresh DB, both remedies end to end through the real routes), `src/server/restFloor.test.js` (18), `src/server/seatRules.test.js` (5).

### MERGE-13-SMOKE-ENV — the browser smoke is three-red locally unless you pass CI's env dials — NOTED (not a product bug)
Cost twenty minutes at MERGE-13 and would cost it again, so it is written down. `npm start` + `npm run smoke:browser` against a plain server fails three tests with `agent build for … failed: 429 {"error":"Too many requests"}` and one console-error red — **and it fails them identically on main**, which is how it was cleared. It is not a regression and not a flake.

The cause is `RATE_LIMIT_CHAT_MAX` (10/min, agentProfiles.js), which MONEY-1 job 4 keyed per-IP: every synthetic owner the smoke builds comes from 127.0.0.1 with no `x-forwarded-for`, so the whole suite shares ONE bucket and the eleventh build of the run is refused. `.github/workflows/deploy.yml` starts its server with `RATE_LIMIT_MAX=100000 RATE_LIMIT_CHAT_MAX=100000 HAND_PAUSE_MS=600 HOME_PAUSE_MS=600 NOTIFY_ENABLED=0` in a scratch data dir, which is why CI never sees it. Locally, do the same:

    mkdir -p /tmp/smoke-data && cd /tmp/smoke-data
    PORT=<yours> NOTIFY_ENABLED=0 RATE_LIMIT_MAX=100000 RATE_LIMIT_CHAT_MAX=100000       HAND_PAUSE_MS=600 HOME_PAUSE_MS=600 node /path/to/src/index.js

With those, smoke is 8/8 and `test:home2` 20/20 on the same server, in that order, exactly as CI runs them. Two further notes for whoever automates this: the budget is spent by ONE smoke run, so a second run against the same process is red however clean the tree is — restart between runs; and `npx playwright test client/e2e/desk.spec.js` from the repo root resolves the root's Playwright rather than the client's and dies with "No tests found" on a `test.use()` parse error. Run it as its own header says, `cd client && npx playwright test e2e/desk.spec.js`.

### MONEY-2 job 3 — the house takes a rake, and five older assertions had to be rewritten to the new rule
Not a bug: a deliberate product change, recorded here because Testing law #5 requires the reasoning to be written down where somebody re-reading a red test can find it.

**The rule that changed.** A casino table now takes a percentage of each pot, capped in big blinds (`src/server/rake.js`, `RAKE_PERCENT` / `RAKE_CAP_BB`), off the winner's stack the moment the pot is awarded. Never at a home table. The engine is untouched — it still awards the whole pot and `game.test.js`'s own conservation law still holds on the result it produces; the table skims the felt afterwards.

**The consequence five tests encoded.** "The winner keeps the whole pot" and "the deltas sum to zero" were both true and are both now false in a precise way: a hand still never MAKES chips, but a raked hand REMOVES some from the felt, so a per-seat net sums to minus the cut. Every one of the five is rewritten to that rule rather than loosened, and each reads the cut off the product (`result.rake.total`, `table.seatRakePaid(seat)`) instead of recomputing it, so a rake that went somewhere other than the seat it was charged to fails them:

- `table.session.test.js` — "result.deltas … summing to zero" → summing to minus `result.rake.total`; "the winner nets what he was paid"; "SESSION_END carries the numbers the ceremony prints".
- `table.seats.test.js` — "no chips created or destroyed by the rebuild" → the felt lost exactly what `table.seatRake` says the house took.
- `table.events.test.js` — "the winner has all of it" → all of it but the rake.
- `table.casinoStart.test.js` — "the winner keeps the engine-awarded stack" → less the cut.
- `scripts/verify-multi-seat.js` and `scripts/verify-watch-v2.js` — the same two rules, in the e2e group. Both were red on `npm run test:e2e` before the rewrite and green after; 7/7 now.

**One thing the rake got right the second time, and it is worth knowing about.** The first version raked `result.pot`, which on a hand that ends to a fold still contains the winner's own uncalled bet: raise 300 into a 20 blind, everybody folds, `pot` is 320 and what he actually won is 20. ### BUG-134 (second regression) — a man in a hand could not be picked up, which after BUG-211 meant never — FIXED
**CLOSED on main.** BUG-134's rule — you cannot lift a man out of the MIDDLE of a hand, because his chips are in the pot — was written when the kitchen table was often idle, so the refusal was a rare and informative "no". BUG-211 made the table always live, and a rule that fires every time is not a refusal, it is a wall: HOME-2 job 5 (pick him up and put him down) became unreachable for the very household BUG-211 exists for.

Jens's instruction: *"Carry must work around a live hand rather than being blocked by one: lifting is allowed in the gap between hands, and a grab during a hand is honoured as soon as that hand finishes, with the agent showing he is mid-hand until then rather than the tap doing nothing."*

**The mechanism — a deferred grab, in three parts.**

1. `useCarry.js` — a refused long press no longer throws the gesture away. The press object is KEPT (`press.refused = true`) rather than cleared, and `onRefuse` tells the screen to remember the grab. A press that has been refused is a HELD REQUEST rather than an undecided one, so travel past `PRESS_SLOP` no longer cancels it: the finger may move and its position is tracked, because it is carrying him somewhere. Only a press that has not yet been answered is still cancelled by travel, which is what keeps a scroll from lifting somebody.
2. `HomeScreen.jsx` — `canLiftNow` is named once (it had been inline; the deferral has to ask the same question a second time and two copies would be two rules), and `pendingLift` holds the agent who was reached for. An effect watches for the hand ending and then calls `pick()` — the same door the roster's CARRY button has always used, so no second carry mode was invented.
3. `pick()` decides between two cases for itself. **Finger still there:** he comes up INTO it, at the point it has reached, with the fixture under it already lit, and the same gesture puts him down. **Finger gone:** he waits for a fresh press, exactly as the roster's CARRY button does, so no stray pointerup can place him.

**And he says so meanwhile**, which is the half that stops the tap from reading as nothing having happened: the bubble reads "I am in a hand. I will come when it is done." and, unlike every other line the room shows, it does NOT fade — it stands until the lift it is explaining. The body also wears `data-awaiting-lift="true"` and a slow 1.5s beat (`home1.css`), stopped dead under `prefers-reduced-motion`.

New regressions: `useCarry.test.jsx` gains three — `lands in the finger still holding him when the hand ends`, `waits for a fresh press once the finger has gone`, and `the finger may travel while the grab waits, and he comes up under it`. `HomeScreen.test.jsx` gains `BUG-134: a seated agent comes up on a long press in the gap between hands` and `BUG-134: a grab during a hand says so, and he comes up when the hand ends`, both driving the kitchen table's own spectator socket so the two states are real rather than assumed.

**`scripts/home2.spec.js` needed a measured budget, not merely a bigger one.** The three job-5 carry cases assert an unchanged rule — a long press lifts him — but the moment it comes true is now "at the latest, the end of the hand he was in". Instrumented across three full runs against a real server at `HAND_PAUSE_MS`/`HOME_PAUSE_MS=600`, the wait from pointer-down to `.is-carried` measured 0.2s, 3.9s, 6.0s, 6.9s, 8.0s, 9.0s, 9.5s, 13.6s and 14.6s. ### BUG-26 — Min-raise loop, again: +10 into a 400-chip pot until the stacks were in — RESOLVED 2026-09-05
**Severity:** Medium (gameplay quality; also inflates LLM cost and arena runtimes)
**Where:** `src/server/table.js` (`_raiseOffer`, `_buildAiGameState`, `_disciplineAction`), constants in `src/server/pace.js`
**Predecessor:** BUG-13, closed 2026-08-29 on the strength of Tree 2's sizing directives and the `RAISES THIS STREET: n` briefing line. Those were a *request* to the model, and the loop came back in tonight's playtest. Recorded as a fresh entry rather than reopening BUG-13, because the diagnosis changed: **a model offered "raise 10–1000" keeps taking the 10, so the table stops offering it.**
**Fix (RAISE-1, `f77d4f9`):**
(a) a raise is at least `max(min legal raise, currentBet + ⅓ pot)` and never above the jam — an agent who cannot afford the floor may still shove, because all-in is the one raise that is always big enough. Undersized raises are rounded up and logged `[agent] undersized raise → X`.
(b) at four aggressive actions the street is CAPPED and the only raise left is the jam: call, fold or all-in, exactly as a capped street works in a cardroom. That is what guarantees the round terminates.
One seam does both jobs — the offer is built once, put in the briefing, and enforced on the way back in; a floor that lived only in the prompt would be a suggestion, one that lived only in the enforcement would keep showing the agent a size the table intends to overwrite. The floor is a fraction of the POT, so it does not bite heads-up preflop where the engine's own minimum is already larger — which was never the case the playtest complained about.
**Dials:** `RAISE_MIN_POT_FRACTION` (default 1/3), `RAISE_CAP_PER_STREET` (default 4), both env-dialable in `src/server/pace.js`.
**Test:** `pace.test.js` (10 cases on the two dials) and `table.raise.test.js` (11 cases through a real Table, including a street of nothing but minimum raises now terminating).

- Branch cycling within a worktree: use `git fetch origin && git checkout -B feature/next main`. The naive `git checkout main && git pull && git checkout -b feature/next` fails because git only allows one worktree per branch, and main is already checked out in C:\Projects\ai-poker.
